## Context

健身房管理系統目前已有完整的使用者管理和個人資料系統，但缺少生日欄位。需要在資料庫、後端 API 和前端表單中統一添加此欄位，以支持會員生日相關的業務需求。

## Goals / Non-Goals

**Goals:**
- 在使用者註冊流程中支持可選的生日欄位
- 在會員個人資料頁面允許修改生日
- 後端 API 正確驗證和儲存生日資訊
- 前端提供友善的日期選擇界面
- 編寫單元測試和整合測試確保功能完整性

**Non-Goals:**
- 生日相關的業務邏輯（如生日賀狀）
- 統計或報告功能
- 修改現有的認證機制

## Decisions

### 1. 資料庫欄位設計
**決策**: 在 USER 表添加 `birthday` 欄位，類型為 `DATE`，允許 NULL
**理由**:
- 生日是可選的，不影響基本的使用者功能
- DATE 類型適合儲存日期，避免時區問題
- NULL 表示未提供生日

**考慮的選項**:
- TIMESTAMP with timezone - 會產生不必要的時區複雜性
- VARCHAR - 不利於日期查詢和驗證

### 2. 前端日期選擇器
**決策**: 使用 HTML5 原生 `<input type="date">` 加上 Tailwind CSS 樣式
**理由**:
- 原生支援，無需額外依賴
- 行動設備支援友善
- Tailwind CSS 已在項目中使用

**考慮的選項**:
- 第三方日期選擇器庫（如 flatpickr）- 增加依賴
- 手動日期輸入 - 用戶體驗較差

### 3. API 驗證策略
**決策**: 後端驗證日期格式和年齡合理性（至少 13 歲）
**理由**:
- GDPR 等隱私法規建議只收集合法年齡的資訊
- 防止輸入無效日期

### 4. 修改權限
**決策**: 使用者只能修改自己的生日，需要認證但無需特殊角色
**理由**: 符合現有的個人資料修改權限模式

## Risks / Trade-offs

| 風險 | 緩解方案 |
|------|---------|
| 舊使用者記錄缺少生日 | 遷移時設為 NULL，UI 提示補充 |
| 日期格式在不同瀏覽器差異 | 後端統一驗證 ISO 8601 格式 |
| 前後端日期格式不一致 | 統一使用 ISO 8601 (YYYY-MM-DD) |

## Migration Plan

1. **資料庫**: 執行遷移新增 `birthday` 欄位到 USER 表（允許 NULL）
2. **後端**:
   - 修改 User Entity 加入 birthday
   - 更新註冊和個人資料 API 端點
   - 執行 `npm run init:schema`
3. **前端**: 更新註冊和個人資料頁面
4. **測試**: 執行完整的測試套件確認功能

回滾策略: 刪除 `birthday` 欄位（已有資料備份）
